PHẦN 2: PHÂN TÍCH CẤU TRÚC DOMAIN (THỰC THỂ DỮ LIỆU) & MỐI QUAN HỆ
--------------------------------------------------------------------------------
Dựa vào thư mục `model` và cấu trúc hệ thống mới nhất, hệ thống được chia làm 5 Nhóm Nghiệp vụ (Domains) chính:

1. QUẢN LÝ XÁC THỰC VÀ NGƯỜI DÙNG (Auth & User Domain) - [MỚI CẬP NHẬT]
   - `AppUser`: Quản lý thông tin người dùng, mật khẩu đã mã hóa, và quyền (Role) (Admin, User...).
   - `RefreshToken`: Quản lý token làm mới phiên đăng nhập nhằm duy trì an toàn và hiệu lực cho JWT.
   
2. QUẢN LÝ MÃ NGUỒN VÀ DỰ ÁN (Source Management Domain)
   - `SourceProject`: Lưu thông tin tổng quan của dự án mã nguồn cần phân tích.
   - `SourceFile`: Lưu thông tin từng file mã nguồn bên trong project.
   - `SourceAnalysisResult`: Lưu kết quả phân tích tĩnh (Static Analysis) cho từng file.

3. QUẢN LÝ TRI THỨC API (API Knowledge Base Domain)
   - `ApiDocument` & `ApiDocumentVersion`: Quản lý tài liệu API theo các phiên bản (Versioning) khác nhau.
   - `ApiEndpoint`: Thông tin chi tiết của 1 API (Path, Method, Description...).
   - `ApiParameter`: Các tham số (Query, Path, Header) của một API.
   - `ApiSchema` & `ApiSchemaField`: Định nghĩa cấu trúc dữ liệu Payload (Body Request/Response).
   - `EndpointSchemaMap`: Bảng trung gian ánh xạ nhiều-nhiều giữa Endpoint và Schema.

4. QUẢN LÝ XỬ LÝ AI & VECTOR DB (AI Processing & Vector Search Domain) - [MỚI CẬP NHẬT]
   - `AiSkill`: Định nghĩa các loại kỹ năng AI (Prompt mẫu, model cần dùng).
   - `AiJobLog`: Bảng theo dõi tiến độ công việc AI qua RabbitMQ (PENDING -> RUNNING -> SUCCESS/FAILED).
   - `LegacyInferenceLog`: Nhật ký theo dõi kết quả trích xuất từ code cũ (Legacy Code).
   - *Hệ thống nhúng PgVector*: Cơ sở dữ liệu Vector lưu trữ Embeddings cho các API Endpoint để tìm kiếm theo ngữ nghĩa (Semantic Search).

5. QUẢN LÝ KIỂM THỬ (Testing Domain)
   - `TestCase`, `TestCaseInput`, `TestCaseAssertion`: Định nghĩa kịch bản test, đầu vào và điều kiện pass/fail cho API.
   - `TestRun`, `TestRunItem`, `TestResult`: Quản lý các lần chạy test, HTTP Request Builder và kết quả cuối cùng.

--------------------------------------------------------------------------------
PHẦN 3: CHI TIẾT CÁC LUỒNG HOẠT ĐỘNG (WORKFLOWS) TỪNG BƯỚC MỘT
--------------------------------------------------------------------------------

► LUỒNG 1: XÁC THỰC VÀ PHÂN QUYỀN (AUTHENTICATION & AUTHORIZATION FLOW)
1. Người dùng gửi `LoginRequest` tới `AuthController`.
2. `AuthService` kiểm tra thông tin thông qua `CustomUserDetailsService` và xác thực mật khẩu (`PasswordConfig`).
3. Nếu hợp lệ, `JwtService` tạo ra AccessToken (sống ngắn) và lưu RefreshToken vào database. Trả về `AuthTokenResponse`.
4. Mọi request sau đó từ Frontend tới hệ thống đều đi qua `JwtAuthenticationFilter`. Nếu có token hợp lệ, Security Context được thiết lập cho User để phân quyền vào từng Controller.

► LUỒNG 2: UPLOAD MÃ NGUỒN & PHÂN TÍCH TĨNH (STATIC ANALYSIS)
1. Frontend gửi thông tin file qua `SourceFileController`.
2. Dữ liệu thô được lưu vào cơ sở dữ liệu (`SourceFile`).
3. Dịch vụ `JavaSourceAnalyzer` sẽ tiến hành quét cấu trúc nội dung mã nguồn để tìm các Pattern đặc trưng (như Servlet, Controller).
4. Phân tích ra thông tin sơ bộ và lưu vào `SourceAnalysisResult` để định cỡ việc có cần gửi gọi AI bóc tách chi tiết hay không.

► LUỒNG 3: AI ĐA MODEL, HÀNG ĐỢI & PHÂN TÍCH BẤT ĐỒNG BỘ (ASYNC MULTI-MODEL AI FLOW)
1. Khởi tạo: Controller kích hoạt `AiTaskProducer`, tạo Job `PENDING` trong `AiJobLog`, đẩy ID vào hàng đợi RabbitMQ và trả kết quả 202 Accepted cho Frontend ngay lập tức.
2. Tiêu thụ: `AiTaskConsumer` nhận Message, đổi trạng thái Job sang `RUNNING`.
3. Chuẩn bị Prompt: `AiTaskPersistenceService` lấy dữ liệu mã nguồn, kết hợp `AiPromptConstants` để chuẩn bị nội dung chuẩn gửi đi AI.
4. AI Router: `AiModelRouterService` xác định sẽ dùng Model AI nào thông qua Interface chung `LlmClientService`.
   - Nếu hệ thống cấu hình gọi Gemini: Sử dụng `GeminiApiClientServiceImpl` và `GeminiWebClientConfig`.
   - Nếu hệ thống cấu hình gọi Ollama (cho mô hình Local): Sử dụng `OllamaApiClientServiceImpl` và `OllamaWebClientConfig`.
5. Làm sạch dữ liệu: Kết quả văn bản từ LLM sẽ được module `AiJsonParserService` cắt tỉa và xử lý (Self-healing). Nó giúp parse an toàn để loại bỏ lỗi JSON bị thiếu hoặc bọc bởi Markdown block.
6. Lưu trữ: Hệ thống ánh xạ JSON thành các Entity (`ApiEndpoint`, `ApiSchema`) thông qua `AiTaskPersistenceService` và lưu DB. Job được chuyển sang trạng thái `SUCCESS`.

► LUỒNG 4: LÀM GIÀU TÀI LIỆU API & TÌM KIẾM VECTOR (ENRICHMENT & VECTOR RAG FLOW)
1. Sau khi API đã được bóc tách từ mã nguồn, `DocumentEnrichmentService` được gọi.
2. Hệ thống gọi LLM AI một lần nữa để sinh ra các bản mô tả dễ hiểu, đầy đủ hơn và gắn thêm thông tin OpenAPI Fragments.
3. Bản tóm tắt API này được chuyển thành Vector Embeddings qua `EmbeddingService`.
4. Vector này được lưu thẳng vào database Postgres qua `VectorSearchService` (Sử dụng extension `pgvector` - đã khởi tạo trong V2__Init_pgvector.sql).
5. Sau này cho phép Frontend tìm kiếm Endpoint bằng ngôn ngữ tự nhiên (Semantic Search).

► LUỒNG 5: QUẢN LÝ TÀI LIỆU VÀ XUẤT OPENAPI (SWAGGER GENERATION)
1. Người dùng chọn các API Endpoint gom nhóm thành `ApiDocument` với `ApiDocumentVersion` cụ thể.
2. Thông qua `OpenApiGeneratorController`, hệ thống gọi `OpenApiGeneratorService`.
3. Service thu thập đệ quy toàn bộ cấu trúc Endpoint, Parameter, Schema Map từ Database và tự động render ra file JSON hoặc YAML theo đúng chuẩn kỹ thuật OpenAPI 3.0.

► LUỒNG 6: TẠO TEST CASE BẰNG AI VÀ THỰC THI (AI TEST GENERATION & EXECUTION)
1. Frontend yêu cầu hệ thống sinh test case. Hệ thống dựa vào cấu hình API Endpoint, gọi qua AI Router để sinh kịch bản `TestCase`, tự động điền `TestCaseInput` (Payload ảo) và `TestCaseAssertion` (Kết quả mong muốn như HTTP 200, Match Body).
2. Khi User nhấn Run (`ExecuteTestRunRequest`), `TestRunService` duyệt qua từng `TestRunItem`.
3. Hệ thống sử dụng `TestRequestBuilder` (trong package runner) để bắn Request HTTP thực tế tới máy chủ cần test.
4. Đối chiếu HTTP Response với bảng Assertion, sau đó lưu lại kết quả Pass/Fail vào `TestResult`.

--------------------------------------------------------------------------------
PHẦN 4: CHI TIẾT VAI TRÒ CÁC TẦNG TRONG CODE (CODE LAYERS ROLE)
--------------------------------------------------------------------------------
- controller: Nơi tiếp nhận Request HTTP/REST, cấu hình Swagger annotations, gọi thẳng vào các tầng Service, hoàn toàn không chứa nghiệp vụ xử lý dữ liệu phức tạp.
- dto: Tách biệt rõ giữa payload từ người dùng `req` (Request) và dữ liệu trả về `res` (Response), chứa các Validator annotations.
- security & config: Nơi định cấu hình Filter xác thực JWT, WebClient Builder (định tuyến Timeouts cho AI Model), cấu hình RabbitMQ, khai báo DB Datasources riêng cho VectorDB.
- repository: Kế thừa JpaRepository, xử lý tương tác cơ sở dữ liệu.
- service: Nơi chứa 100% logic của hệ thống. Luôn được chia thành Interface và `impl` (Implementation).
  + Các thư mục con như `ai`, `analysis`, `rabbitmq`, `runner` được chia ra chuyên biệt để gánh các luồng logic lõi như AST Regex phân tích mã nguồn cũ, AI Routing / Parser / Parsing khôi phục lỗi, và Request Builder chạy Test.
- model: Chứa các Entity Hibernate mapping chính xác với Table dưới Postgres.
- resources/db/migration: Thư mục chứa các script của Flyway để tự động khởi tạo cơ sở dữ liệu (Schema) và cài đặt các Extensions (Ví dụ: pgvector).
- exception: Chặn các ngoại lệ từ mọi nơi (Ví dụ: `AiJsonParseException`) và chuẩn hoá thành HTTP Error Responses chung thông qua `GlobalExceptionHandler`.

TỔNG KẾT BỨC TRANH LỚN HỆ THỐNG
Dự án AI ToolCheck Backend là một nền tảng chuyên nghiệp (Enterprise-level) với khả năng:
(1) Bảo mật người dùng bằng JWT Role-Based.
(2) Trích xuất và phân tích mã (Legacy code) bằng hệ thống AI Đa Model (Gemini Pro/Ollama Qwen) vận hành không đồng bộ qua RabbitMQ.
(3) Tự động sửa chữa lỗi JSON của AI (Self-healing parser).
(4) Áp dụng kiến trúc RAG (Retrieval-Augmented Generation) thông qua hệ quản trị dữ liệu Vector PgVector.
(5) Quản lý, xuất chuẩn tài liệu OpenAPI và Tự động thực thi Auto Execution Testing HTTP.

Kiến trúc "Package-by-Feature" chia thành các module nhỏ giúp hệ thống linh hoạt, dễ nâng cấp và có thể đáp ứng tính đa nhiệm phân tán lớn trong tương lai.
