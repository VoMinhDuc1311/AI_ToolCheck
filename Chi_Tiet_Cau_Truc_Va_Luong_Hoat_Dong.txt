DỰ ÁN: AI TOOLCHECK BACKEND (SPRING BOOT)
================================================================================

Tài liệu này trình bày MỘT CÁCH ĐẦY ĐỦ NHẤT VÀ KHÔNG VIẾT TẮT về:
1. Toàn bộ cây thư mục vật lý chi tiết tới TỪNG FILE của mã nguồn.
2. Cấu trúc Domain Model (Các thực thể dữ liệu và mối quan hệ).
3. 4 Luồng hoạt động (Workflows) cốt lõi của toàn bộ hệ thống.
4. Vai trò thực tế của từng Layer Code.

PHẦN 2: PHÂN TÍCH CẤU TRÚC DOMAIN (THỰC THỂ DỮ LIỆU) & MỐI QUAN HỆ
--------------------------------------------------------------------------------
Dựa vào thư mục `model`, hệ thống được chia làm 4 Nhóm Nghiệp vụ (Domains) chính:

1. QUẢN LÝ MÃ NGUỒN VÀ DỰ ÁN (Source Management Domain)
   - `SourceProject`: Lưu thông tin tổng quan của dự án mã nguồn cần phân tích.
   - `SourceFile`: Lưu thông tin từng file mã nguồn bên trong project.
   - `SourceAnalysisResult`: Lưu kết quả phân tích tĩnh (Static Analysis) cho từng file (file này là Controller, Servlet, hay Utils...).

2. QUẢN LÝ TRI THỨC API (API Knowledge Base Domain)
   - `ApiDocument` & `ApiDocumentVersion`: Quản lý tài liệu API theo các phiên bản (Versioning) khác nhau.
   - `ApiEndpoint`: Thông tin chi tiết của 1 API (Path, Method, Description...).
   - `ApiParameter`: Các tham số (Query, Path, Header) của một API.
   - `ApiSchema` & `ApiSchemaField`: Định nghĩa cấu trúc dữ liệu Payload (Body Request/Response).
   - `EndpointSchemaMap`: Bảng trung gian ánh xạ nhiều-nhiều giữa Endpoint và Schema.

3. QUẢN LÝ XỬ LÝ AI (AI Processing Domain)
   - `AiSkill`: Định nghĩa các loại kỹ năng AI (Prompt mẫu, model cần dùng).
   - `AiJobLog`: Bảng theo dõi tiến độ công việc AI (PENDING -> RUNNING -> SUCCESS/FAILED).
   - `LegacyInferenceLog`: Nhật ký theo dõi kết quả trích xuất từ code cũ (Legacy Code).

4. QUẢN LÝ KIỂM THỬ (Testing Domain)
   - `TestCase`, `TestCaseInput`, `TestCaseAssertion`: Định nghĩa kịch bản test, đầu vào và điều kiện pass/fail (Assertions) cho API.
   - `TestRun`, `TestRunItem`, `TestResult`: Quản lý các lần chạy test (Test Execution), trạng thái từng item và kết quả cuối cùng.

PHẦN 3: CHI TIẾT CÁC LUỒNG HOẠT ĐỘNG (WORKFLOWS) TỪNG BƯỚC MỘT
--------------------------------------------------------------------------------
Hệ thống của bạn không chỉ có 1 luồng, mà có 4 luồng hoạt động chính liên kết với nhau thành một Vòng đời khép kín (Lifecycle):

► LUỒNG 1: UPLOAD MÃ NGUỒN & PHÂN TÍCH TĨNH (STATIC ANALYSIS)
Mục đích: Đọc hiểu và phân loại code trước khi gọi AI để tiết kiệm chi phí API.
1. Frontend gọi API nén hoặc gửi thông tin Project/File lên `SourceProjectController` / `SourceFileController`.
2. Dữ liệu thô được lưu vào DB (`SourceProject`, `SourceFile`).
3. `JavaSourceAnalyzer` (và các lớp trong package `service/analysis`) được kích hoạt để quét bằng Regex/AST.
4. Phân tích ra được `AnalysisSignals` (dấu hiệu nhận biết) xem file này có chứa Annotation (ví dụ `@RestController`), hay cấu trúc Servlet (`doGet`, `doPost`).
5. Nếu file đáng chú ý, nó lưu vào `SourceAnalysisResult` và chuyển sang LUỒNG 2.

► LUỒNG 2: BÓC TÁCH API BẰNG GOOGLE GEMINI (ASYNCHRONOUS AI FLOW)
Mục đích: Biến mã nguồn hỗn độn thành tài liệu API chuẩn cấu trúc.
1. Khởi tạo: Controller kích hoạt `AiTaskProducer`, tạo Job `PENDING` trong `AiJobLog`, đẩy ID vào RabbitMQ và lập tức trả HTTP 202 cho Frontend.
2. Tiêu thụ: `AiTaskConsumer` nhận Message, đổi Job thành `RUNNING`.
3. Chuẩn bị AI: Hệ thống lấy mã nguồn, ghép với `AiSkill` (Prompt), tạo thành yêu cầu hoàn chỉnh.
4. Gọi API: `GeminiApiClientServiceImpl` dùng WebClient gọi sang Google Gemini. Cơ chế Retry được kích hoạt nếu mạng chập chờn.
5. Xử lý phản hồi: Hệ thống phân tích cú pháp JSON AI trả về (xử lý các trường hợp JSON bị cắt cụt).
6. Lưu trữ: Parse thành công, lưu trực tiếp thành các Entity `ApiEndpoint`, `ApiParameter`, `ApiSchema` vào cơ sở dữ liệu.
7. Hoàn tất: Cập nhật `AiJobLog` sang `SUCCESS`. Frontend polling API thấy SUCCESS thì tự động tải dữ liệu API Endpoints về hiển thị.

► LUỒNG 3: QUẢN LÝ TÀI LIỆU VÀ XUẤT OPENAPI (SWAGGER GENERATION)
Mục đích: Tổ chức các API vừa quét được thành các bộ tài liệu có phiên bản.
1. Người dùng chọn các `ApiEndpoint` mong muốn và gộp lại thành một `ApiDocument` thông qua `ApiDocumentController`.
2. Có thể tạo nhiều `ApiDocumentVersion` (ví dụ: v1.0, v2.0) cho cùng một tài liệu nếu code legacy có sự thay đổi.
3. Người dùng gọi `OpenApiGeneratorController`.
4. Hệ thống sẽ lấy cấu trúc trong Database (Endpoints, Parameters, Schemas) và render ra file JSON/YAML chuẩn định dạng OpenAPI 3.0.
5. Người dùng tải file này về và ném vào Swagger UI hoặc Postman để sử dụng.

► LUỒNG 4: SINH TEST CASE VÀ THỰC THI KIỂM THỬ (TEST EXECUTION)
Mục đích: Đảm bảo các API vừa bóc tách vẫn chạy đúng logic cũ.
1. Kích hoạt AI tạo Test: Gọi API yêu cầu sinh tự động kịch bản test cho một Endpoint.
2. AI tạo ra `TestCase`, các biến `TestCaseInput` (Body, Params cần truyền) và `TestCaseAssertion` (Chờ đợi mã 200, Body chứa chuỗi "Success",...).
3. Chạy Test: Người dùng tạo `TestRun` và ấn Execute (`ExecuteTestRunRequest`).
4. Hệ thống gọi `TestRunService` duyệt qua tất cả `TestRunItem`. Nó sẽ tạo HTTP Client thực hiện lệnh gọi thật (Real HTTP Call) tới API nội bộ hoặc API hệ thống gốc.
5. So sánh kết quả: Phản hồi trả về được đối chiếu với `TestCaseAssertion`.
6. Lưu kết quả: Cập nhật pass/fail vào `TestResult` và phản hồi tổng thể `TestRun` cho người dùng.

--------------------------------------------------------------------------------
PHẦN 4: CHI TIẾT VAI TRÒ CÁC TẦNG TRONG CODE (CODE LAYERS ROLE)
--------------------------------------------------------------------------------
- controllers: Đóng vai trò là cửa ngõ (API Gateway nội bộ), chỉ chứa các annotations (@PostMapping, @GetMapping) và gọi DTO/Service. KHÔNG chứa logic AI.
- dto: Chia gói rất khoa học (aijoblog/req, aijoblog/res). Tách bạch rõ giữa Request Body và Response JSON, giúp dễ maintain.
- rabbitmq: Chứa các file quan trọng như AiTaskProducer (ném job vào queue) và AiTaskConsumer (bốc job từ queue, phối hợp với các Service khác để xử lý tác vụ nặng AI).
- services/analysis: Điểm sáng của dự án. Không phụ thuộc AI ngay từ đầu mà dùng thuật toán nội bộ đánh giá code (Scoring). File code nào đạt điểm qua ngưỡng mới gọi Gemini -> Giảm chi phí token AI đáng kể.

TỔNG KẾT BỨC TRANH LỚN
Dự án AI ToolCheck là một hệ thống khép kín đi từ:
(1) Mã Nguồn Thô -> (2) Phân tích Tĩnh -> (3) Trích xuất bằng LLM (RabbitMQ/Gemini) -> (4) Quản lý Tri thức (OpenAPI) -> (5) Auto Testing.
Cấu trúc Package-by-Feature (chia thư mục dto, service theo nghiệp vụ) giúp code có thể mở rộng lên hàng trăm tính năng mà không bị rối. Kiến trúc Queue giúp hệ thống cực kỳ chịu tải (Fault-Tolerant).
